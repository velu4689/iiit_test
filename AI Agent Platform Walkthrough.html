1. Which OAuth flow each hop uses

  • 3LO (three-legged OAuth): a user is present and signs in or approves access.
  • 2LO (two-legged OAuth, client credentials): a machine authenticates as itself, with no user.
  • OBO (on-behalf-of token exchange): the gateway swaps the user's token for a narrower one, keeping the user as sub.

2. Cost and token accounting

  • Every agent has exactly one identity (1:1) and one owner team: agent-1 and agent-2 → team-1, agent-3 → team-2, orchestrator → team-platform.
  • Agents call models with only their own agent token and a fixed X-TFY-METADATA header such as {"team":"team-1","agent":"agent-1","session_id":"…"}.
  • Budget rules match on metadata.team (per team) and metadata.agent (per agent). Tracking counts against every matching rule; the first matching rule decides allow or block.
  • Rate limits per metadata.agent are the first defence against runaway loops.
  • Metadata is set by agent code from config, never from user input or model output. Monthly, compare metadata against the agent identity recorded in gateway traces.
  • Keep metadata keys short and consistent; values are capped at 128 characters, and custom identifiers belong inside X-TFY-METADATA, not separate headers.

4. Filtering data by team inside an MCP server

Key rule: the team always comes from the validated token, never from tool arguments. The model fills in arguments, so a prompt must not be able to widen access.

  1. Validate the token: signature against Okta JWKS, iss, aud, exp, and the server's scope (e.g. mcp3.tools).
  2. Build a caller context: user = sub, teams = groups (only ai-users-*).
  3. Apply it to every data access, ideally with database row-level security so a missed WHERE clause cannot leak.
  4. Deny by default: no team claim means no rows.

Common mistakes:

  • Groups claim missing or too large: filter the claim in Okta (starts with "ai-users-").
  • Stale membership: keep access tokens short (10 minutes).
  • Caching: include the team set in every cache key.
  • Leaky results: errors and counts such as "3 of 40 hidden" reveal data; return only what the caller may see.
  • Users in several teams: decide between the union of their teams' data (simpler) and one team per session (safer).
  • mcp-3: re-check on the server that the tool is allowed for the caller's team, even though the Virtual MCP already hides it.

5. SaaS MCP notes

  • Atlassian: per-user OAuth respects each user's own Atlassian permissions. Confirm Atlassian will accept the TrueFoundry gateway as an OAuth client and that an admin allows your gateway's domain.
  • Grafana: Grafana Cloud MCP is user-scoped by Grafana RBAC; the self-run open-source server is scoped to whatever service account it uses.
  • DataHub: DataHub's guidance is never to share one token across users; use OAuth or individual credentials.
  • MongoDB: team service accounts give team-level, not user-level, control. MongoDB sees only the team DB user; gateway traces record the person.
  • Confirm with TrueFoundry that when an agent calls on a user's behalf, the gateway uses the 3LO token that user approved earlier.

6. XAA and ID-JAG

  • ID-JAG is the IETF draft grant; XAA (Cross App Access) is Okta's product name; Enterprise-Managed Authorization is the MCP extension built on it.
  • The MCP extension went stable in June 2026. Atlassian is among the listed supporting servers; Grafana, DataHub and MongoDB are not yet confirmed.
  • The vendor's authorization server must accept the ID-JAG grant and trust your Okta org as an issuer.
  • TrueFoundry's MCP form already offers an "ID-JAG (XAA)" grant type, so moving Atlassian is a one-screen change once Okta and Atlassian are set up.
  • Benefits over 3LO: no consent prompts, IT policy decides access, revocation in one place, no long-lived user tokens stored in the gateway.
  • Agent-to-agent ID-JAG needs the separate Okta for AI Agents product; MCP hops don't.

7. Kill switch

  • Deactivating an app or user in Okta stops new tokens; tokens already issued stay valid until they expire. Hence 10-minute access tokens.
  • Okta's agent kill switch is manual today. Automatic layers are yours: gateway rate limits, budgets and guardrails, plus step and token caps in agent code.
  • Removing an agent or MCP in the TrueFoundry gateway is the instant layer: the next call gets 403.
  • Agents must treat 401/403 as "stop", back off on 429 and budget errors, and report themselves offline. This is a go-live requirement.
  • Severity ladder: L1 throttle → L2 contain → L3 suspend agent → L4 isolate team → L5 global stop. Name who may trigger L4 and L5.

8. Check before you build

  1. Atlassian accepts the gateway as an OAuth client (or supports XAA for your tenant).
  2. 3LO tokens stored per user are used when an agent acts on that user's behalf.
  3. Agent identity is beta in TrueFoundry: pin a version and test the full chain.
  4. Okta API Access Management is licensed (required for token exchange).
  5. Grafana Cloud or self-managed? This decides per-user OAuth vs per-team service accounts.
